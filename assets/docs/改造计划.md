# 政策库抓取系统改造计划（v1）

## 0. 背景与目标
现有仓库以脚本式方式实现列表与详情抓取，数据以 JSON 文件落盘。为提升可维护性、稳定性与长期运行能力，需进行模块化重构，满足：
- 稳定可持续运行（幂等、增量、重试、限速）。
- 结构化存储与任务编排（SQLite 任务队列）。
- 原始数据可追溯（Raw HTML/JSON、附件落盘）。
- 质量监控与报警（空正文率、失败率、耗时）。


## 1. 现状评估（AS-IS）
- 代码形态：`test.py`、`guo_wu_yuan_zheng_ce.py` 为脚本式，职责耦合（请求、解析、存储混在一起）。
- 数据存储：
  - 列表结果保存为 `gov_policies/policy_管理条例_p1-100.json`。
  - 详情结果保存为 `gov_policies/details/*.json`，包含正文与附件链接。
  - 未保存 Raw HTML；附件已支持下载至 `gov_policies/attachments/`。
- 可靠性：
  - 有基本 sleep/限速与错误捕获，但缺少统一重试/退避策略。
  - 缺少幂等写入（无 UPSERT/唯一键校验）。
  - 无任务队列/状态机，列表与详情耦合。
- 监控：缺少质量检测（空正文阈值）、失败率指标、报警链路。


## 2. 目标架构（TO-BE）
采用“六层”分层：Scheduler / Fetcher / Parser / Pipeline / Storage / Monitor，并模块化目录：

```
crawler/
  config.py
  fetcher.py
  parser/
    list_parser.py
    detail_parser.py
  pipeline.py
  storage/
    sqlite_store.py
    file_store.py
  tasks/
    list_task.py
    detail_task.py
  monitor.py
  main.py
```

核心特性：
- 列表任务与详情任务解耦；详情失败不阻塞列表。
- 幂等：统一主键（`id` 或 `index` 或 `url_hash`）+ UPSERT。
- 增量：基于时间窗口或唯一键去重。
- 原始数据落盘：列表 Raw JSON（可选关键字段），详情 Raw HTML 与附件原文件。
- 质量检测：正文长度阈值与空正文率报警。


## 3. 数据模型与 SQLite 表设计

表一：`policy_list`
- `id TEXT PRIMARY KEY`（推荐：接口返回的 `id` 或 `index`）
- `url TEXT`
- `pubtime TEXT`
- `title TEXT`
- `status TEXT`（`PENDING_DETAIL`/`DONE`/`FAILED`）
- `retry INT`
- `created_at TEXT`
- `updated_at TEXT`

表二：`policy_detail`
- `id TEXT PRIMARY KEY`（对应 `policy_list.id`）
- `content TEXT`
- `attachments_json TEXT`
- `parser_version TEXT`
- `raw_html_path TEXT`
- 元数据：`fetched_at`、`parsed_at`、`raw_html_sha256`、`source_url`

说明：
- 附件不单独建表，先以 `attachments_json` 保存（后续可拆表）。
- 写入策略统一使用 UPSERT，保障幂等。


## 4. 里程碑与交付物

M1：项目骨架与核心抽离（预期 0.5~1 天）
- 初始化目录结构与 `config.py`。
- 抽离 `fetcher.py`（Session、Headers、Cookies、重试、退避、限速）。
- 抽离 `parser/list_parser.py`、`parser/detail_parser.py`（版本化）。
- `storage/sqlite_store.py`：建库建表、UPSERT 通用方法。
- `tasks/list_task.py`：抓列表 → 解析 → 写 `policy_list`（状态置 `PENDING_DETAIL`）。
- 交付：可单独跑“列表入库”。

M2：详情任务与原始数据落盘（预期 0.5~1 天）
- `tasks/detail_task.py`：拉取 `PENDING_DETAIL` → 抓详情 → 保存 Raw HTML → 解析正文与附件 → 下载附件 → 写 `policy_detail` → 状态流转。
- `storage/file_store.py`：Raw HTML 与附件落盘路径策略与 SHA256 计算。
- 质量检测：`content length < 阈值` 记为解析失败并重试。
- 交付：可批量补齐详情，保证幂等与失败重试。

M3：调度与增量（预期 0.5 天）
- `main.py` + `Scheduler`：
  - 每日增量抓取（基于时间窗口或唯一键去重）。
  - 列表与详情任务分频率独立调度（apscheduler/cron）。
- 完善限速与状态码处理（403/429 降速/延迟、5xx 重试）。
- 交付：一键可运行的日常任务调度脚本。

M4：监控与日志（预期 0.5 天）
- `monitor.py`：统计成功率、失败率、空正文比例、耗时。
- 日志规范化与失败样本采样落盘。
- 阈值报警（控制台/文件；可扩展到飞书/钉钉）。
- 交付：质量报表与关键指标输出。

M5：可选增强（Scrapy/Redis）（可选 1 天）
- 迁移到 Scrapy（内置队列、去重、重试、限速、pipeline）。
- 以 Redis/SQLite 作为队列后端（视数据量与并发而定）。


## 5. 幂等与增量策略
- 唯一主键：优先使用接口返回 `id`；若缺失，以 `url` 的 `md5(url)` 作为 `url_hash`。
- 列表入库：对同一 `id` UPSERT；若已存在，`status` 不回退。
- 详情处理：
  - 首次处理：`status=PENDING_DETAIL → DONE`；失败 `retry+1`，超过阈值标记 `FAILED`。
  - 内容更新：若页面变更（ETag/Last-Modified 或 HTML 变更），写新 `parser_version` 与 `raw_html_sha256`。
- 增量窗口：默认近 30 天；可配置。


## 6. 错误处理、重试与限速
- 重试：网络超时、连接失败、5xx → 指数退避 + 抖动，最多 3 次。
- 状态码：
  - 403：换 UA / 延迟 / 换 session。
  - 429：明显限流 → 降速 + 延迟。
  - 404：记 `NOT_FOUND` 不重试。
- 访问节奏：
  - 列表：0.5~1.0 s/次。
  - 详情：1~3 s/次（`random.uniform(1.0, 2.5)`）。
  - 每 N 次额外 sleep（如每 20 次 sleep 5s）。


## 7. 质量检测与报警
- 规则：
  - `content length < 200` 视为解析失败。
  - `正文为空比例 > 10%` 判定结构变更风险。
- 报警：记录到 `monitor.log` 与汇总报表；可扩展消息通知。


## 8. 运行与交付方式
- 单次运行：
  - 列表任务：`python -m crawler.tasks.list_task --keyword 管理条例 --days 30`
  - 详情任务：`python -m crawler.tasks.detail_task --max-retry 5`
- 定时：
  - `apscheduler` 定时每日跑列表与详情。
  - 或 `cron` 调度两个命令，时间错开。
- 数据输出：
  - SQLite：任务与结构化数据。
  - 文件系统：Raw HTML、附件、日志、质量报表。


## 9. 风险与应对
- 页面结构变更：通过“正文长度阈值 + 空正文率”快速发现；Parser 版本化便于热修。
- 反爬/限流：403/429 策略、限速与随机化、Session 池化。
- Cookie 失效：统一刷新策略与可配置注入。
- 大规模下载：附件单独队列并限速，失败不阻塞正文入库。


## 10. 验收标准（关键指标）
- 成功率：列表 ≥ 99%，详情 ≥ 95%。
- 失败可恢复：重试后成功率 ≥ 98%。
- 空正文比例 ≤ 5%，超过阈值触发报警。
- 幂等：重复跑不产生重复记录或脏文件。
- 可追溯：每条详情具备 `fetched_at / parsed_at / parser_version / raw_html_sha256 / source_url`。


## 11. 实施清单（按模块）
- config.py：常量、限速、重试、阈值、路径、DB 连接串。
- fetcher.py：Session、Headers/Cookies、重试与退避、状态码处理、限速节流。
- parser/list_parser.py：抽取 `listVO` 与核心字段，健壮容错。
- parser/detail_parser.py：正文候选选择、附件解析、版本标识。
- storage/sqlite_store.py：初始化表、UPSERT、状态机更新。
- storage/file_store.py：Raw HTML 与附件落盘、命名与 SHA 校验。
- pipeline.py：去重、校验、标准化与合并（列表+详情）。
- tasks/list_task.py：入队 `policy_list`、置 `PENDING_DETAIL`。
- tasks/detail_task.py：按状态消费、落盘、解析、状态流转与重试。
- monitor.py：指标采集、质量检测、报表输出。
- main.py：命令入口、调度编排。


—— 以上为 v1 可落地改造方案，优先完成 M1~M3，即可达到“稳态运行 + 可追溯 + 质量可控”。后续再按需演进至 Scrapy/Redis 架构。
