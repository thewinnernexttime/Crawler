## 第02章：分层架构与职责边界——Scheduler/Fetcher/Parser/Pipeline/Storage/Monitor

### 1. 你将学到什么（本章目标）
- **学会画边界**：每层“负责什么、不负责什么”，这是架构师最核心的能力之一。
- **学会选抽象**：为什么要拆分列表/详情任务？为什么要把请求/解析/存储分开？
- **学会用边界管理复杂度**：当需求增加（增量、重试、监控、并发）时不至于把代码写烂。

---

### 2. 分层不是“看起来更高级”，而是为了控制变化
抓取系统会变的东西非常多：
- 站点反爬策略会变（403/429/验证码/限流）
- 页面结构会变（正文容器变、附件链接变）
- 存储会变（先 JSON，后 SQLite，再上对象存储/ES）
- 调度会变（手动跑 → cron → apscheduler → 分布式队列）

**架构的目标**：让变化只影响一层，而不是全局联动。

---

### 3. 六层职责清单（你必须背下来）
下面按“职责 / 输入输出 / 失败策略 / 本项目落点”描述。

#### 3.1 Scheduler（调度层）
- **职责**：决定“什么时候运行哪些任务”，并控制频率与顺序。
- **输入输出**：输入是“时间/策略”，输出是“任务执行”。
- **失败策略**：任务失败不应影响其它任务；可以错峰运行。
- **本项目落点**：当前用命令行手动触发（`crawler/main.py`），后续可接 cron/apscheduler。

#### 3.2 Fetcher（请求层）
- **职责**：把网络请求做得“可靠且礼貌”：超时、重试、退避、状态码处理、限速。
- **输入输出**：输入 URL+参数，输出 response（JSON/text/stream）。
- **失败策略**：网络失败是常态；应重试并退避；对 403/429 要降速等待。
- **本项目落点**：`crawler/fetcher.py`（`Fetcher.get_json/get_text/get_response`）。

> 关键思维：Fetcher 不关心“业务字段”，只关心“把数据拿回来”。

#### 3.3 Parser（解析层）
- **职责**：把 response 解析为结构化数据（字段、正文、附件列表）。
- **输入输出**：输入原始 JSON/HTML，输出结构化 dict/list。
- **失败策略**：解析失败应该能被识别（空正文/字段缺失），最好能版本化方便回放。
- **本项目落点**：
  - 列表：`crawler/parser/list_parser.py`
  - 详情：`crawler/parser/detail_parser.py`

> 关键思维：Parser 要“容错 + 可演进”，网页结构变了只改 Parser。

#### 3.4 Pipeline（数据管道层）
- **职责**：数据清洗、标准化、合并、去重、规则校验（ETL）。
- **输入输出**：输入 parser 的结构化结果，输出“可写入存储的最终形态”。
- **失败策略**：将“坏数据”转为“可解释的失败”，不要静默污染数据库。
- **本项目落点**：`crawler/pipeline.py` 目前是预留扩展点（直通），后续可放清洗/结构化抽取逻辑。

#### 3.5 Storage（存储层）
- **职责**：把数据保存得“幂等、可查、可恢复”，以及提供任务提取能力。
- **输入输出**：
  - 输入：可写入的结构化数据
  - 输出：持久化结果、任务队列能力（取待处理/更新状态）
- **失败策略**：写入失败要可重试；幂等保证重复运行不产生脏数据。
- **本项目落点**：
  - SQLite：`crawler/storage/sqlite_store.py`
  - 文件落盘：`crawler/storage/file_store.py`

#### 3.6 Monitor（监控层）
- **职责**：回答“系统跑得怎样”：成功率、失败率、空正文率、吞吐、耗时；并报警。
- **输入输出**：输入日志/计数器/事件，输出报表或告警信号。
- **失败策略**：监控本身不能影响主流程（最多降级）。
- **本项目落点**：`crawler/monitor.py` 提供日志初始化与计数器雏形。

---

### 4. 边界如何落到代码结构？
这不是“文件夹美化”，而是“组织复杂度”：
- `crawler/tasks/*`：任务编排（把多个层串起来）
- `crawler/fetcher.py`：统一网络请求能力
- `crawler/parser/*`：解析逻辑集中，便于版本化与替换
- `crawler/storage/*`：持久化与幂等语义集中

**经验法则**：当你发现一个文件里同时出现“HTTP + HTML解析 + SQL + 文件写入”，就该拆层了。

---

### 5. 常见坑（边界被破坏的信号）
- **Fetcher 里开始写业务字段处理**：例如在 get_json 里挑字段、拼主键，这是边界污染。
- **Parser 里直接写数据库**：会导致“解析逻辑”和“存储策略”耦合，后续换存储非常痛苦。
- **Task 里堆满 if/else**：说明缺少 Pipeline 或策略模式，业务规则没有被抽象出来。

---

### 6. 练习（建立“边界敏感度”）
1) 打开 `tasks/detail_task.py`，用笔标注每一行属于哪一层（Fetcher/Parser/Storage/Monitor/Task）。
2) 设想要新增“代理池”与“UA 池”，你会把代码加在哪里？为什么不是加在 task 里？
3) 设想页面结构变了导致空正文，你修哪里？如何用 `PARSER_VERSION` 管理历史数据？
