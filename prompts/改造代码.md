**“先列表 → 再详情 → 结构化存储”** 的政府政策库抓取任务

# 1. 架构总览

把爬虫拆成 6 层：

## ✅ 1）Scheduler（调度层）

决定何时抓什么：

* 每天定时跑
* 任务队列（例如：列表任务、详情任务、附件下载任务）
* 重试策略（失败再跑）

## ✅ 2）Fetcher（请求层）

负责发 HTTP 请求：

* session 管理
* headers/cookies/代理/限速
* 自动重试
* 自动处理 403/5xx
* 支持缓存（ETag / If-Modified-Since）

## ✅ 3）Parser（解析层）

负责把 “response” 变成结构化数据：

* 列表解析器（JSON）
* 详情解析器（HTML）
* 附件解析器（PDF/DOC）

⚠️ Parser 一定要做到：**容错 + 版本化**
（网页结构一变，只改 parser，不动架构）

## ✅ 4）Pipeline（数据管道）

负责：

* 去重
* 校验
* 数据清洗
* 标准化字段
* 数据合并（列表字段 + 详情字段）

## ✅ 5）Storage（存储层）

负责：

* 原始数据（Raw HTML/JSON）保存
* 结构化数据（JSON/数据库）保存
* 附件文件存储（本地/对象存储）

## ✅ 6）Monitor（监控层）

负责：

* 成功率、失败率
* 解析空正文比例
* 结构变更报警
* 任务耗时
* 日志追踪
* 指标可视化（Prometheus/Grafana 可选）

# 2. 可靠性设计要点（重中之重）

下面这些策略，会决定你这个爬虫能不能跑三个月不崩。

---

## 2.1 任务分层：列表任务与详情任务拆开

原因：

* 列表抓取很快，详情抓取慢且容易失败
* 详情抓失败不应影响列表采集
* 可以灵活控制抓取频率（列表每天跑，详情按需跑）

---

## 2.2 幂等性（Idempotency）：重复跑不会产生脏数据

这是可靠爬虫的灵魂。

✅ 具体做法：

* 所有记录使用稳定主键：`id` 或 `index` 或 `url hash`
* 每次写入数据库时 `UPSERT`
* 附件文件按 `id + 文件名` 存储，存在就跳过

---

## 2.3 增量策略：别每次全量重抓

有两种成熟方案：

### ✅ 方案A：基于时间窗口

* 每天只抓最近 30 天的列表页
* 然后更新详情（未抓取或更新的）

### ✅ 方案B：基于去重键

* 用 `id/index` 作为唯一键
* 列表抓到后，如果 `id` 已存在，跳过详情

---

## 2.4 重试与降级：失败不是错误，是常态

每一个请求都应该有标准化策略：

### ✅ Fetch 层重试策略

* 重试次数：3 次
* 退避：指数退避 + 随机抖动
* 只重试：网络超时、5xx、连接失败

### ✅ 状态码处理

* 200：正常
* 301/302：跟随
* 403：触发降级（换 UA / 换 session / 延迟）
* 429：明显限流 → 降速 + 增加等待
* 404：记录为 NOT_FOUND，不重试
* 5xx：重试

---

## 2.5 限速与访问节奏：别把自己当 API 用户

政府站很容易限流。
建议节奏：

* 列表 API：0.5~1.0 秒/次
* 详情页：1~3 秒/次（加随机）
* 附件下载：单独队列 + 限速

✅ 推荐 `random.uniform(1.0, 2.5)`
✅ 每 N 次请求休息更久（例如 20 次 sleep 5 秒）

---

## 2.6 “原始数据落盘”是救命的

不要只存结构化结果。

### 必须存：

* 列表响应 raw JSON（或至少保存关键字段）
* 每个详情页 raw HTML
* 附件原文件

这样当：

* 解析器出 bug
* 页面结构变化
* 你想补字段/修正字段
  都可以**不用重新爬**，直接重新 parse。

# 5. 强烈推荐：用 SQLite 做任务队列（最简单、最可靠）

你用 SQLite 就能做一个完整的爬虫系统：

### 表结构建议：

**policy_list**

* id TEXT PRIMARY KEY
* url TEXT
* pubtime TEXT
* title TEXT
* status TEXT
* retry INT
* created_at
* updated_at

**policy_detail**

* id TEXT PRIMARY KEY
* content TEXT
* attachments_json TEXT
* parser_version TEXT
* raw_html_path TEXT

然后：

* `status=PENDING_DETAIL` 的做详情任务
* 抓成功改成 `DONE`
* 抓失败 retry+1
* retry>5 改为 FAILED

---

# 6. 防结构变更（最难的问题）

网页结构变了你要立刻发现，否则会产生**空正文数据**。

✅ 解决方案：**质量检测 + 报警**

例如：

* `content length < 200` 认为解析失败
* `正文为空比例 > 10%` 认为结构变更
* 报警：写日志 + 发邮件/钉钉/飞书（可选）

---

# 7. 可复现、可审计：每条数据都要带版本

每条 detail 写：

* `fetched_at`
* `parsed_at`
* `parser_version`
* `raw_html_sha256`
* `source_url`

当你发现某些字段解析错了，你可以回溯是哪一版 parser 做的。
